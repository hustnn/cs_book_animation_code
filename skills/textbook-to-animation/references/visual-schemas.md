## 1. 为什么要先选图式

“图式”指一段讲解反复使用的画面结构：数据长什么样、住在哪里、怎么移动、代价怎么被看见。
没有先选图式就写场景，画面几乎一定退化成“框 + 线 + 标签”：一个写着“小段”的框飞进一个写着“大段”的框，
观众看到的是方框换了位置，看不到数据发生了什么。旁白讲得再清楚，画面也只是在配合念稿，讲解就显得干巴。

图式在第 2 步（教学设计）为每个单元选定，写进 design.md；第 3 步写分镜时，每一拍的画面动作都在这个图式里展开。
组件在 `assets/motion-canvas/schemas.ts`（复制到 `motion-canvas/src/lib/schemas.ts`）。

## 2. 选图式的四个问题与“空框测试”

对每条 P0 机制，依次回答：

| 问题 | 回答决定什么 | 例子 |
|---|---|---|
| 1. 机制里流动、变化的**东西**是什么？ | 它要有身份：一个块就是一条数据，带真实的键和值，不是写着类别名的框 | 键值对、请求、消息、页、段、比特 |
| 2. 它住在哪些**地方**？ | 全景图的分区，整个单元不换图 | 内存 / 磁盘；客户端 / 服务器；第 0 / 1 / 2 层 |
| 3. 它经历哪些**步骤**？每一步改变了什么状态？ | 一步一拍（或一个 `at()`），主角一次动一个 | 追加日志 → 有序插入 → 冻结 → 刷盘 → 合并 |
| 4. 观众该**数**什么？ | 用计数器、计量条把代价放到画面上 | 读了几次磁盘、写了几遍、占了几份空间 |

**空框测试**：随便停在一帧，静音看画面。框里装的是不是具体的数据？如果框里只有它自己的名字（“小段”“缓存”“索引”），
而这一拍要讲的恰恰是“里面的数据怎么变”，就是空框：换成有身份的数据块，或者先用真实数据走一遍，再缩成抽象的框（见“先具体后抽象”）。
只表示“有这么个组件”、不讲内部变化的框（比如架构图里的“负载均衡器”）不算空框。

## 3. 图式清单

| 图式 | 解决什么 | 画面怎么做 | 写法 |
|---|---|---|---|
| **数据有身份** | 看不出“哪条数据去了哪里” | 每条数据一个小块，显示真实的键和值（`handful:44662`）；它从一个容器真的走到另一个容器 | `KV`：`appear` / `moveTo` / `clone`（复制一份走，原件留下） |
| **有序插入、其余让位** | “始终有序”只是一句话 | 新块落下前，比它大的块先往后让一格，新块再落进空位 | `Slots.insertSorted(kv)` |
| **追加** | “只追加、不排序”和“有序”分不清 | 日志区里新块总是排到末尾，乱序也照排 | `Slots.append(kv)` |
| **覆盖与作废** | 旧值去哪了 | 同键新值：块的值原地换掉并闪一下；作废：变灰、划一道红线，之后再清走 | `KV.setValue(v)`、`KV.stale()`（划线自动设 `qa-ignore` key） |
| **先具体后抽象** | 抽象的“小段并进大段”看不懂 | 先用 3–4 个装着真实数据的容器完整演一遍（谁留下、谁被丢掉），再把它们缩成只表示大小的块，讲一般规律 | 具体那一遍不少于 2–3 拍；抽象的块要和刚才的容器有视觉延续（同色、同位置缩小过去） |
| **全景图常驻** | 每拍换一张图，观众找不到自己在哪 | 整个单元一张图：分区固定（左内存、右磁盘），写入、读取、合并都在这张图上走；换场景时下一个场景从上一个的终态开始 | `zone()` 画分区；把终态写成一个函数，下一个场景直接复原 |
| **推镜头** | 结构里的细节太小，或者要“钻进”某个部分 | 整个 world 节点放大、平移到目标；镜头外的东西先淡出（否则会被 QA 判出画）；看完再拉回 | `Cam.focus(p, zoom)` / `Cam.reset()`；**不要用 Motion Canvas 的 `Camera` 组件**（QA 看不到它里面的内容） |
| **剖面放大** | 某个部件的内部机制（过滤器、索引页）要单独讲，又不能丢掉全景 | 全景压暗、虚化退后；被讲的部件放大画在前景（不随镜头动的 HUD 层），演完淡出、全景恢复 | `W.opacity(0.25)` + `W.filters.blur(6)`；前景放 HUD 层 |
| **计数器 / 计量条** | 代价（读几次盘、写几遍、占多少）只念不看 | 角落一个“磁盘读 N 次”，每读一次 `bump()`；大小用竖条涨到上限线 | `Counter`、`Meter`（值都是信号，可补间） |
| **共享坐标轴** | “范围不重叠”“只和重叠的部分合并”靠说 | 几层画在同一根轴上（键 a→z、时间、地址）：块的位置和宽度就是它的范围，重叠一眼可见 | 一个 `X(key)` 映射函数，所有层都用它；重叠区域用半透明色带标出 |
| **格子 / 比特行** | 位图、哈希、布隆过滤器只念公式 | 一行格子，置位时变色；查询时箭头指到几个位置，0 的格子标红、1 的格子标黄 | `Bits.set` / `mark`、`hashLines` |
| **对比表** | 两种方案的取舍说完就忘 | 行是维度、列是方案，用长短条代替“高 / 低”；书里没给数字的，标“示意” | Rect 条 + `tag(…, '示意')` |
| **前后并排 / 时间线** | 状态变化、时序 | 见 `pedagogy.md` 第 4 节的深度演示模式库 | — |
| **代码逐行** | 算法、SQL、配置 | 代码随讲解逐行高亮，旁边的数据结构同步变化 | MC 的 `Code` 组件（选区高亮、`edit` 改代码） |

原文之外的内容（比如原文只有一句的机制，补上它真实的工作方式）在画面角落加 `tag(…, '延伸 · 原文之外')`，
书里没有具体数字的定性对比加 `tag(…, '示意')`。规则见 SKILL.md 第 1 步的“深度延伸”。

## 4. 组合：全景图、推镜头、剖面放大

场景的节点分三层，镜头只动 world：

```tsx
import {Cam, Counter, KV, Slots, tag, zone} from '../../lib/schemas';

const W = new Node({});     // world：全景图的一切都放这里
const HUD = new Node({});   // 不随镜头动的：计数器、角标、剖面放大的前景
view.add([W, HUD]);
const cam = new Cam(W);

// 推镜头：先把镜头外的东西淡出，再推
yield* beat('r4',
  all(...offCamera.map(n => n.opacity(0, 0.4)), cam.focus([300, -75], 1.6, 1.2)),
  at('稀疏索引', index.opacity(1, 0.5)),
);

// 剖面放大：全景退后，前景放大讲内部
yield* beat('r8', all(W.opacity(0.25, 0.6), W.filters.blur(6, 0.6), cutaway.opacity(1, 0.6)));
```

- 一个单元的几个场景共用一份坐标常量（如 `stage.ts`），后一个场景开头直接复原前一个场景的终态，画面无缝衔接。
- 推镜头放大 ≤ 2 倍、每次 ≥ 1s；推近后至少讲一拍再拉回。
- 剖面放大的前景和它在全景里对应的部件要有连线或同色，观众知道放大的是哪一块。

## 5. 节奏：一次一步、主角走慢、演示拍

- **一次只动一个主角。** 机制的每一步（一条数据落位、一个段被合并）单独占一个 `at()` 或一拍。几个块一起飞，只在要演“同时”时用。
- **主角走慢。** 数据块、消息这类主角的移动 ≥ 0.8s，关键变换（合并、分裂、换层）≥ 1.2s；拍首留 0.3s 让观众看清起点。
  渲染 QA 的 `fast-move`（看得清的文字不到 0.5s 走 150px 以上）会把太快的移动列出来。
- **同一个块的连续移动串成一条 `chain`。** 拆进几个 `at()` 时，前一段还没走完后一段就开始，两个补间同时改 `position`，
  块会在两条路径之间抽动。`lint_scenes.py` 会对这种情况报 warn。
- **演示拍。** 变换本身就要几秒、旁白却一句话就说完时，在 beats.json 里给这一拍加 `"hold": 秒数`（0–10），
  旁白念完后静音这么久给画面演完。不要为了凑时长把旁白拖长，也不要把动作压缩到旁白的长度里。
- **重复一次。** 最关键的一步（比如合并时只留最新值）可以用第二组数据再演一遍，第二遍更快。

## 6. 两个工具里常被忽略的表达手段

| 工具 | 手段 | 用来做什么 |
|---|---|---|
| MC | 信号与 `createComputed` | 派生量自动跟着变：计数器、柱高、连线端点随数据实时更新，不用逐个补间 |
| MC | `Line` 的 `start` / `end` 补间、`lineDash` + `lineDashOffset` | 线“画出来”；虚线流动表示数据在流 |
| MC | `node.reparent(新父节点)` | 换父节点但保持画面位置：块从一个容器“交给”另一个容器后，跟着新容器一起移动 |
| MC | `filters`（blur、brightness、grayscale） | 剖面放大时背景退后；作废的内容变灰 |
| MC | `Layout`（flex） | 表格、列表、卡片自动排版 |
| MC | `Code` | 代码逐行高亮、改代码的动画 |
| MC | `Img` / `SVG`（本地文件） | 图标、示意图元。`Icon` 组件要在线请求图标库，无头渲染时不可用 |
| MC | `spawn` / `loop` | 背景里持续进行的流（写入不断进来）而不占主线时间 |
| Manim | `MovingCameraScene` | 推镜头、跟随 |
| Manim | `TransformMatchingShapes` / `TransformMatchingStrings` | 公式、文字按相同部分变形，推导过程看得见 |
| Manim | `Graph`、`Table`、`Code` | 图结构、表格、代码 |
| Manim | `MoveAlongPath`、`ShowPassingFlash` | 沿路径移动；沿线一闪而过表示数据流 |
| Manim | `ValueTracker` + `always_redraw` | 一个参数驱动曲线、读数联动 |

## 7. 外部图表工具怎么取舍

能静态出图的工具（架构图生成器之类）不进渲染管线，原因有三：
- 输出是静态 SVG / PNG，元素没有 id，拆不开、做不成分步动画；
- 自带字体常常没有中文字形（2026-11 试过 open-diagram v0.6：中文渲染成缺字方块）；
- 风格和 theme 不一致，拼进视频会跳。

可以借鉴的是它们的版式：面板分区、图块排布、“示例走查”面板（一边是结构，一边是一条数据的走法），以及把常见版式错误起了名字逐条检查的做法。

## 8. 示例：LSM 树的写入、读取、压缩合并

原文对这一节只有几段话：写入先进内存里的有序结构，满了刷成磁盘上的有序段；读从新到旧查；后台合并；两种合并策略各一两句。
用上面的图式，扩成三个场景、42 拍、约 4 分钟（时长由旁白决定）：

| 场景 | 拍 | 图式 | 画面 |
|---|---|---|---|
| 写入 | 1–2 | 全景图常驻 | 四个乱序的键先排好，点出“乱序写进来、磁盘上要有序”；左内存右磁盘两个分区出现 |
| | 3–5 | 数据有身份、追加 | `handiwork:45521` 出现：先复制一份追加到日志末尾（“只用于崩溃恢复”），再走进内存里的有序结构 |
| | 6–8 | 有序插入、覆盖 | 再写三个键，比它大的块让位；同一个键再写一次：日志照样追加，内存里原地换值 |
| | 9–13 | 计量条、先后两步 | 大小条涨到上限：这棵树冻结、挪到一边，新写入进新树；冻结的树逐块复制到磁盘成为一个有序段（一扫而过表示顺序写）；日志里对应的条目划掉、清走 |
| 读取 | 1–4 | 计数器、推镜头 | 查询块从新到旧逐段查，右上角“磁盘读 N 次”逐次加一；到最旧的段推镜头：稀疏索引 → 块 → 找到值 |
| | 5–6 | 计数器 | 查一个不存在的键：一路查到底，每段都白读一次 |
| | 7–11 | 剖面放大、格子 | 全景退后，一行比特位放到前面：写入时三个位置置 1；查询时有一个 0 就“一定不在”；全 1 只能“可能在”，再演一次误判；每键约 10 位 → 误判约 1%（标“延伸”） |
| | 12 | 计数器 | 回到全景，再查那个不存在的键：三个过滤器都说不在，磁盘读停在 0 |
| 合并 | 1–2 | 计数器 | 段越攒越多，读最坏要查 6 段；被覆盖的旧值划掉，还占着空间 |
| | 3–5 | 先具体后抽象 | 四个装着真实键值的段合并：同一个键出现三次，只留最新的；再缩成小 / 中 / 大三级，讲“攒够几个就往上并” |
| | 6–7 | 计数器、计量条 | 同一个键的新旧值散在几级里，读要多查；合并期间新旧两份同时占空间 |
| | 8–14 | 共享坐标轴 | 每层画在同一根 a→z 键轴上：第 0 层重叠、往下不重叠；挑一段只和下一层重叠的几段合并；读时第 1 层往下每层最多查一段；同一份数据沉到底被写了 3 次 |
| | 15–16 | 对比表 | 两种策略在“读要查的段 / 占用空间 / 写盘次数”上的长短条（示意），以及哪些系统用哪种 |

这个示例里踩过的坑都已写进规则：不用 `Camera` 组件、推镜头前淡出镜头外内容、同一个块的连续移动串成一条 `chain`、
引导线画在不透明块的下面（先 add 线再 add 块）、复制块出发时才显形（否则会和原块叠在一起）。
