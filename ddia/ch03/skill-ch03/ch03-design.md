## 单元 U1：最简单的数据库：一行一行追加

- 钩子：世界上最简单的数据库，只用两个 Bash 函数？
- P0 机制（≤ 3）：追加写与全表扫描；索引是派生的路标；读快与写慢的权衡
- 学习目标（新手测试题，至少一题带 [走查]）：
  1. [走查] 文件里已有三行（123456 London；42 Golden Gate；42 Exploratorium），db_get 42 要扫几行、返回哪个值？再追加一行 42 的新值后呢？
  2. [走查] 给这三行建一个“键 → 行号”路标：db_get 42 现在要扫几行？删掉路标，数据变了吗、查询变慢了吗？
  3. 为什么写很难比单纯追加更快？每加一个索引，一次写要多做几件事？
- 常见误区：
  - 索引是数据库“自带”的免费加速；
  - 写和读可以同时变快。
- 核心画面 / 主线例子：追加写日志文件（每行一个键值对，旧值变灰）；db_get 42 两次写，第二次盖住第一次（Golden Gate Bridge → Exploratorium）。
- 图式（visual-schemas.md 的四个问题）：
  - 流动的东西：键值对小块（42:Exploratorium），追加进文件；扫描线从头扫到尾
  - 分区：左日志文件（逐行长），右路标索引（键 → 行号）
  - 步骤：追加 → 扫全文件 → 建路标 → 跳过去
  - 要数的代价：扫描的行数（计数器）、一次写的动作数（追加 1 次 vs 追加 + 更新索引）
  - 推镜头 / 剖面放大：推近看 tail -n 1 怎么挑出最后一行
- 深度演示：O(n) 扫描线——文件从 3 行长到 3000 行，查找时间翻倍再翻倍；天平：读快 vs 写慢。
- 叙事弧：钩子（两个 Bash 函数）→ 直觉（追加写很快，扫文件很慢）→ 机制（索引是派生的路标、写要更新索引）→ 证据（O(n)、追加写最快）→ 边界（并发、回收空间、写一半的记录留待后面）→ 回扣（选索引就是在读快与写慢之间选）。

## 单元 U2：哈希索引：键就是地址

- 钩子：查一个键，能不能不用从头扫到尾？
- P0 机制（≤ 3）：键就是地址；段切分与压缩合并；查不到与查一片
- 学习目标（新手测试题，至少一题带 [走查]）：
  1. [走查] 内存哈希表 {123456: 0, 42: 64}，查 42 要几步？哪步碰磁盘、哪步不碰？
  2. [走查] 图 3-2 的 12 格段压成 3 格：哪 3 格留下、为什么是它们？再并上图 3-3 的段 2，24 格变 4 格，哪 4 格留下？
  3. [走查] 查一个不存在的键，要查几个段的哈希表？查 kitty00000 到 kitty99999 之间所有键，要查多少次？
- 常见误区：
  - 哈希表在内存里，所以读永远不用碰磁盘；
  - 删一条记录就是把它擦掉。
- 核心画面 / 主线例子：猫视频播放计数（mew / purr / yawn / scratch）贯穿全单元；Figure 3-1 按原图复现（内存哈希表 123456 → 0、42 → 64，字节格日志文件，箭头指向文件内位置）；Figure 3-2（12 格 → 3 格）、Figure 3-3（24 格 → 4 格）按原图重新生成。
- 图式（visual-schemas.md 的四个问题）：
  - 流动的东西：键值块（mew:1082）——追加进日志段、复制进哈希表、合并时逐个挑进新段
  - 分区：上内存哈希表（每段一张），下磁盘日志段（越往右越新）；压缩漏斗在中间
  - 步骤：追加 → 更新偏移 → 段满切分 → 压缩去重 → 后台合并 → 删旧段
  - 要数的代价：查一个键要读几次磁盘（计数器）、段数（计量条）、压缩前后格数（12 → 3、24 → 4）

## 单元 U3：排好序的段：SSTable 与 LSM 树

- 钩子：日志越写越长，段越攒越多，怎么收拾？
- P0 机制（≤ 3）：写入路径；读取路径；压缩合并
- 学习目标（新手测试题，至少一题带 [走查]）：

## 单元 U13：排序与写入：列存的两难

- 钩子：列存排好序省了读，写进来怎么办？
- P0 机制（≤ 3）：整行排序与第一排序键；同一份数据多几种排法；写缓冲：LSM 思路复用
- 学习目标（新手测试题，至少一题带 [走查]）：
  1. [走查] 各列独立排序后，第 k 项还对得上同一行吗？按 date_key 排好后，查“上个月”的销售要扫多少行？
  2. [走查] 同一份数据按日期排一份、按产品排一份：查“上个月”用哪份、查“某产品全年”用哪份？
  3. [走查] 往已排序的列文件中间插一行：要重写什么？改走写缓冲后，新写先去哪、查询怎么同时看到磁盘与内存？
- 常见误区：
  - 每列排好序、查哪列都快；
  - 同一份数据只能有一种排法；
  - 列存写不进去。
- 核心画面 / 主线例子：按日期排、只扫上个月——查询优化器跳过其余月份的行；同一份数据多几种排法（C-Store / Vertica）；猫视频回扣——写缓冲批量合并，是 U2/U3 压缩合并思路的复用。
- 图式（visual-schemas.md 的四个问题）：
  - 流动的东西：行（小块）整行整行排序；新写先进内存缓冲、攒够一批再批量并进磁盘列文件
  - 分区：左磁盘列文件（已排序），右内存写缓冲；上查询（同时看两边）
  - 步骤：整行排序 → 第一排序键 → 多几种排法 → 写进缓冲 → 批量合并
  - 要数的代价：查上个月要扫的行数（只扫 300 行 / 一共 3600 行）、几十亿行压成几 KB、写缓冲攒了多少（演示 3 笔；真要到 1000 笔 / 几兆才合并）

- 深度演示：排乱了拼不回来——各列独立排序后，第 k 项对不上同一行，行拼不回去；排序帮压缩——主排序列排好后长段重复值，几十亿行压成几 KB；写缓冲演出——写先进内存、攒够一批再与磁盘列文件合并批量写盘，查询同时查磁盘与内存、优化器把区别藏起来。

## 样片单元选择

**选 U2“哈希索引：键就是地址”（§3.2）做样片。**（沿用 r1 决定，r2 复核仍成立。）

理由：

1. **本章 OLTP 一侧的支点**：哈希索引是第一个完整存储引擎（索引 + 段 + 压缩），U3（SSTable）、U4（B 树）、U5（对决）都在回扣它；做通了它，后面单元的叙事骨架就立住了。
2. **核心画面最强**：Figure 3-1（哈希表 + 字节格文件）、Figure 3-2（12 格 → 3 格）、Figure 3-3（24 格 → 4 格）三张原图改编，画面动作密集，能验证本章最常用的视觉手法（原图拆步演出、逐格变灰、逐键挑最新值）。
3. **覆盖本章主线例子**：猫视频播放计数是全章第一个主线例子，样片做通后，这个例子的视觉资产（12/24 格段、压缩漏斗）可直接复用。
4. **验证本章大头工具链**：纯 Motion Canvas，不涉及 Manim 衔接，能先把 MC 场景、TTS、时间轴、QA、审查这条主线跑通。
5. **规模适中但有挑战**：24 个要点、8 个 P0，估计约 5 分钟，是本章最满的单元之一；样片能测出“上限单元”的分镜节奏控制。
