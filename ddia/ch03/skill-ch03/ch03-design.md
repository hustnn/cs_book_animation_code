## 单元 U1：最简单的数据库：一行一行追加

- 钩子：世界上最简单的数据库，只用两个 Bash 函数？
- 学习目标（新手测试题）：1. db_set / db_get 是怎么存、怎么找的？为什么找是 O(n)？2. 什么是索引？它从哪来、要付什么代价？3. 为什么说“写很难比追加更快”？
- 常见误区：索引是数据库“自带”的免费加速；写和读可以同时变快。
- 核心画面 / 主线例子：追加写日志文件（每行一个键值对，旧值变灰）；db_get 42 两次写，第二次盖住第一次（Golden Gate Bridge → Exploratorium）。
- 深度演示：O(n) 扫描线——文件从几行长到上千行，查找的扫描线越扫越长，记录数翻倍、查找时间翻倍；索引是旁边的路标，指向数据。
- 叙事弧：钩子（两个 Bash 函数）→ 直觉（追加写很快，扫文件很慢）→ 机制（索引是派生的路标、写要更新索引）→ 证据（O(n)、追加写最快）→ 边界（并发、回收空间、写一半的记录留待后面）→ 回扣（选索引就是在读快与写慢之间选）。
- 结尾句：追加写最快，但找东西得从头扫——所以要有路标。

## 单元 U2：哈希索引：键就是地址

- 钩子：查一个键，能不能不用从头扫到尾？
- 学习目标（新手测试题）：1. 内存哈希表里存的是什么？查值要几步？2. Compaction 是什么？它为什么能让段变小？3. 哈希索引的两个局限是什么？
- 常见误区：哈希表在内存里，所以读永远不用碰磁盘；删一条记录就是把它擦掉。
- 核心画面 / 主线例子：猫视频播放计数（mew / purr / yawn / scratch）贯穿全单元；Figure 3-1 按原图复现（内存哈希表 123456 → 0、42 → 64，字节格日志文件，箭头指向文件内位置）；Figure 3-2（12 格 → 3 格）、Figure 3-3（24 格 → 4 格）按原图重新生成。
- 深度演示：压缩演出——12 格逐个变灰、只留 3 格最新值落进压缩段；合并演出——两段并排，每键的最新值逐个挑进合并段；墓碑演示——追加一条删除记录，合并时该键的旧值一起消失。
- 叙事弧：钩子（不用扫全文件）→ 直觉（键 → 偏移 → 磁盘位置，一次 seek）→ 机制（Bitcask、段切分、compaction、后台合并读写不停）→ 证据（猫视频计数、一次 seek vs 零次磁盘 I/O）→ 边界（实现细节五条：格式、墓碑、崩溃恢复、半截记录、并发）→ 局限（键太多放不进内存、范围查询要逐个查）→ 回扣（哈希索引快，但只解决了一种查找）。
- 结尾句：键就是地址，但地址表得放进内存，范围也查不了——下一单元换个思路。

## 单元 U3：排好序的段：SSTable 与 LSM 树

- 钩子：日志越写越长，段越攒越多，怎么收拾？
- 学习目标（新手测试题）：1. SSTable 和日志段有什么区别？2. 稀疏索引是怎么找到键的？3. 写先进内存、崩溃了怎么办？
- 常见误区：排好序就要在磁盘上原地维护顺序；查不存在的键和查存在的键一样快。
- 核心画面 / 主线例子：hand… 开头的键（Figure 3-4 三段归并、Figure 3-5 稀疏索引，按原图重新生成）；猫视频回扣——合并还是“只留最新值”，只是这次键排好了序；memtable → SSTable → 合并的流水线。
- 深度演示：归并演出——三段首键并排比较、最小键逐个抄进输出段，同键旧值变灰丢掉；稀疏索引演出——找 handiwork 时先跳到 handbag 的索引项，再在阴影块内逐格扫到 handiwork；查不存在的键——从 memtable 一路查到最旧的段才敢说没有。
- 叙事弧：钩子（段越攒越多）→ 直觉（排好序，合并就像归并排序）→ 机制（稀疏索引、块压缩、memtable 刷盘）→ 证据（Figure 3-4/3-5、LevelDB / RocksDB / Cassandra / HBase、Lucene 词典）→ 边界（布隆过滤器、两种压缩策略）→ 回扣（大而有序，写快）。
- 结尾句：排好序，内存里不用全记住，磁盘写还是顺序的——这是日志结构学派的完整形态。

## 单元 U4：B 树：把数据切成页

- 钩子：数据多到内存装不下，树怎么长还不倒？
- 学习目标（新手测试题）：1. B 树查一个键要走几步？每步靠什么决定方向？2. 页满了怎么办？树怎么保持平衡？3. 原地覆盖和只追加，崩溃时各怕什么？

## 单元 U13：排序与写入：列存的两难

- 钩子：列存排好序省了读，写进来怎么办？
- 学习目标（新手测试题）：1. 为什么各列不能独立排序？2. 排序怎么帮压缩，又怎么帮查询？3. 列存的写为什么要借 LSM 树的思路？
- 常见误区：每列排好序、查哪列都快；同一份数据只能有一种排法；列存写不进去。
- 核心画面 / 主线例子：按日期排、只扫上个月——查询优化器跳过其余月份的行；同一份数据多几种排法（C-Store / Vertica）；猫视频回扣——写缓冲批量合并，是 U2/U3 压缩合并思路的复用。
- 深度演示：排乱了拼不回来——各列独立排序后，第 k 项对不上同一行，行拼不回去；排序帮压缩——主排序列排好后长段重复值，几十亿行压成几 KB；写缓冲演出——写先进内存、攒够一批再与磁盘列文件合并批量写盘，查询同时查磁盘与内存、优化器把区别藏起来。
- 叙事弧：钩子（排好省了读，写怎么办）→ 直觉（插入顺序最容易，但指定顺序更有用）→ 机制（整行整行排序、第一排序键、第二排序键）→ 证据（按日期排、按产品排、排序帮压缩）→ 边界（越往后的排序键越乱；多几种排法像多个二级索引、但没有指针）→ 转场（读快了、写难了）→ 机制（原地更新行不通、LSM 式写缓冲）→ 回扣（读与写又一次交锋）。
- 结尾句：排法是为查询选的，写是借老办法解决的——列存的账，读和写各记一笔。
